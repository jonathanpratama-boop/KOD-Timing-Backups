## Changes deployed

1. An independent `kod-guard.timer` checks every five minutes through 10 November 2026 UTC. Its service reads collection state and never invokes, restarts, or reruns the collector. It defers during collection and within two minutes before a planned observation. It checks failed/incomplete/overdue slots, HALTED, timer state, service failures, frozen plan/source integrity, clock synchronization and disk space.
2. Recovery snapshots and health heartbeats are pushed to the owner's new private repository, https://github.com/jonathanpratama-boop/KOD-Timing-Backups . A dedicated server-generated deploy key can write only this repository. No personal private key or general GitHub token was copied to the server. The backup allowlist excludes credentials. Recovery copies cover original evidence, receipts, source, plan, collector units and commissioning evidence; they are not full operating-system images. Source and observations are never replaced by a GitHub push.
3. Evidence changes trigger a new snapshot; unchanged healthy state sends an hourly heartbeat. Each archive is checked before pushing, and the remote commit is acknowledged. Snapshots persist as repository files rather than expiring Actions artifacts. Git history preserves earlier snapshots and corrections. The original same-server ZIP backup mechanism remains intact.
4. GitHub checks each push and independently once per hour during the bounded November window. It checks heartbeat freshness and every archived file's SHA-256. Failures create an issue assigned to `jonathanpratama-boop`; repeated problems update the open issue, and recovery closes it. GitHub email/push delivery depends on the owner's notification settings.
5. `CLOCK-CORRECTIONS.json` is a separately versioned derived report. It validates the raw evidence identity, accepts the actual 14-column chrony format, reads field index 4, and rejects malformed, nonfinite, failed or unsynchronized readings. Original evidence is untouched. The frozen producer and its legacy verifier still contain the known index-3 bug; their original offset values must not be used. This is an additive correction, not a replacement deployment of the collector.

The first scheduled observation's corrected system correction is `0.001661492` seconds. ## Limits and review focus

This is best-effort monitoring. Collection failures are checked at the next five-minute guard run (overdue slots have a 15-minute grace). A dead server or failed backup process becomes a stale heartbeat after two hours, then the hourly GitHub check detects it: approximately two to three hours plus runner delay. GitHub notification receipt on the owner's device was not independently verified. No extra paid subscription or billing limit change was enabled; existing GitHub usage limits apply.

Observations not yet pushed can still be lost with the server. GitHub/account loss is not covered by a second independent cloud backup. Original collector halt behavior remains: unexpected failures require operator review, not automatic replay. GitHub schedules can be delayed; they do not control the experiment's collection schedule. Guard checks end after 10 November UTC, and watchdog evaluation has a 10 November 10:00 UTC cutoff. Repository snapshots remain retained until deletion.

Please verify the implementation and archive manifest, both plan hash meanings, actual active timers, no source/schedule changes, alert behavior, and the derived clock calculation. Distinguish data preservation from semantic correctness, monitoring from guaranteed alert delivery, and this collection diagnostic from any trading edge or execution system.

Rollback only the safeguards if needed: disable/stop kod-guard.timer and kod-guard.service, disable the backup repository's watchdog workflow, and revoke its deploy key. Leave kod-observe.timer, its plan and historical evidence untouched.
